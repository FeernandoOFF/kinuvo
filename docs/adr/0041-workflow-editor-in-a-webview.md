---
title: "Workflow editor in a webview"
description: "The Workflow graph is edited in a bundled vanilla page on vendored Drawflow, shown in the Artifacts web view and driven by the ViewModel through its two-way page bridge."
---

Status: Accepted

A Workflow's graph is edited in a web page inside the app's web view for Artifacts (`WebView`: the OS web view in a `SwingPanel` on desktop, `WebView` on Android, `WKWebView` on iOS), not in Compose. The page is hand-written HTML, CSS and JavaScript on Drawflow 0.0.60 (MIT), with no build step, bundler, package manager or framework. Drawflow's minified script, stylesheet and licence are vendored unmodified in `client/ui/composeResources/files/workflow/`; Kotlin inlines them with the page into one document, so the editor works offline and loads nothing remote. The document is wrapped like the Artifact canvas: a script-only sandboxed frame (opaque origin) with a policy that allows only the page's own nonce-marked scripts and inline styles, no network of any kind and no `eval`. Messages cross the frame through the Artifact bridge, so the page works wherever visual editing does. The browser build draws on a canvas and cannot receive page messages, so there the editor shows a note to use the desktop or mobile app. Compose popups that overlap the editor behave as they do over Artifacts.

The page is a view. Its model is the protocol's `Workflow` JSON and Drawflow only draws it: nodes, connections and positions are never persisted or exchanged in Drawflow's own format. Steps are edited inline in their cards: an Agent turn (Agent, prompt, Session), a Model request (prompt, system prompt, model), a Tool call (name with suggestions, JSON arguments), an Approval (question) and a Review (question, value). Step ids are generated as `<kind>-<n>` with the smallest free number (`agent-1`, `model-1`, `tool-1`, `approval-1`, `review-1`) and shown read-only on the card. Each prompt, system, arguments and value field has an "Insert output of…" menu listing the step's ancestors, which inserts `{{steps.<id>.output}}` at the cursor. The page refuses self-edges and duplicate edges; the Server stays the authority on cycles. Steps without a `position` are laid out by longest-path depth and index within the column. When given a `WorkflowRun`, each card shows its step status and a collapsed output or error.

The `WorkflowViewModel` stays the single source of truth, and the page never calls the Server. The messages are small JSON types in `client/app` (`WorkflowEditorMessages`). The page posts each message as `{kinuvo: "workflow", json}`, and the app calls the page through `kinuvoReceive`, as for the design canvas. Kotlin to page: `load` (Workflow, catalog of Agents, models and tools, theme, run), `catalog`, `run` and `theme`. Page to Kotlin: `ready`, `changed` (the whole edited Workflow) and `open_session`. The page sends `changed` only after a user edit that alters the graph, never on load or for a click that moves nothing. `open_session` works for any step with a Session, resolving its Agent as the Server does: an Agent turn's own, else the Workflow's `agentId`, else the first Agent turn's. The ViewModel takes only `steps` and `edges` from `changed`, so fields edited natively are never overwritten. The page reloads its model only on `load`, which the screen sends once ready and when the draft's graph changes from outside the page (a discard or a Server change), never for a change the page made. Tool suggestions are the tools the Workflow's Agent can call, read from its Session capabilities; without an Agent the field is free text. Colours come from the app theme in light and dark.

Everything that is not the graph stays native: the Workflow list, name, trigger and schedule, enable switch, the Agent it runs as, Run and Cancel, the waiting-Approval bar, save and discard, and the run history, whose selected run is the one shown on the graph.
