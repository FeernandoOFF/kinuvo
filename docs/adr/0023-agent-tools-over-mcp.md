---
title: "Agent tools: one service, native and MCP transports"
description: "Kinuvo's tools for Agents are one Server service reached natively or over MCP, scoped to the caller."
---

Tools that let Agents work with one another are one service on the Server. Every call carries a caller scope: the calling Agent, its Session and its delegation depth. The service enforces the scope, so Session tools see only the caller Agent's own Sessions and the child Sessions it delegated, never another Agent's, and never a Hidden Session. The first group, `agent_tools`, is a built-in tool group, always sent to the model and on by default. Its read tools are `agents_list`, `sessions_list`, `sessions_search`, `sessions_read` and `session_status` (Low risk). Its delegation tools are `delegate` (Medium), `delegate_wait` and `subagents` (Low, except `subagents` cancel at Medium).

The same implementation has two transports. Native Agents get the group as built-in tools. External Agents reach it over MCP: the Server serves streamable HTTP at `/mcp`, authenticated by a token minted for one Session when its execution opens and revoked when it closes. When Kinuvo starts an ACP session it passes this server in `session/new` `mcpServers`: HTTP when the harness advertises `mcpCapabilities.http`, otherwise a stdio entry running the hidden `kinuvo mcp-bridge` command, which proxies to the same endpoint and receives its token in the environment, not on the command line. The ACP SDK stays in the JVM-only module. Agents reached through a remote execution grant do not get these tools.

These tools run on the Server, so Kinuvo's own Risk, Approval, Trust and Deny rules govern every call, native or over MCP. An MCP call that needs an Approval shows it in the caller's Kinuvo Session through the execution's Approval broker; Deny rules block it first. Agents never change their own Risk tolerance or Trust rules through these tools.

A second built-in group, `agent_manage`, on by default, lets a native Agent configure itself from chat. It reuses the Server's Settings handlers (`Admin`, MCP management, `HarnessRuntime.configure`), so a chat edit and a Settings edit take the same path. `agent_get`, `mcp_list` and `mcp_test` are Low; `session_configure` and `mcp_login` Medium; `agent_update`, `agent_create`, `mcp_add` and `mcp_remove` High. A tool can describe its call (`Tool.describe`), and the Server builds that text before asking: every change's Approval carries `field: old → new` lines, with secret values (`env`, `headers`) left out. The High tools are `alwaysAsk`: they ask at every Risk tolerance, including `full` and Auto Routines, and offer no Always allow. A call the tool rejects fails before the user is asked.

What an Agent can't loosen from chat, whoever approves: its Risk tolerance (a Session may only be made stricter), Trust rules, Deny rules, where its shell runs, and any tool group this Server doesn't offer. The tools don't take those parameters, and asking for them fails with a message to use Settings. `agent_create` starts from the template, not a copy, so the new Agent gets none of the caller's Memory, Skills, Trust rules or own MCP servers (servers shared with every Agent are still shared). `mcp_add` adds Agent-scoped servers, and `mcp_remove` removes only the Agent's own, and only when the user named it. `mcp_login` shows the sign-in link in an `ask_user` form and completes with the address the user pastes back. External Agents get none of `agent_manage` yet: Kinuvo-side identity for an External Agent is a later step.

`/mcp` answers only loopback peers: External Agents always run on this machine, while the Server may be publicly reachable. Browsers (an `Origin` header), other hosts and requests a proxy forwarded get 403.

Delegation is part of the same service and uses the shared `ExecutionDispatch`, so a native or an External Agent can be the target, and the caller, without special cases. The Server creates a child Session on the target, links it to its parent (parent Session and Agent, depth) and sends it the goal and context as its first message; it never receives the parent's transcript. Foreground calls wait for the child's run and return its final answer; background calls return the Session id and `delegate_wait` fetches the answer. The child's questions and Approvals go through its own Session's brokers, so the user answers them there while the parent waits, but not forever: after 30 minutes unanswered (the Routine rule) the parent's call fails for that child with "waiting on the user", and the child's Session stays open for the user to answer later. Chains are bounded by the Agent's `delegationDepth` (default 2): a Session at that depth is not offered the delegation tools. Stopping a Session stops its running descendants, and cancelling the parent's call stops its foreground child.

A hidden delegation keeps sensitive data on the Server's own device. A Hidden Session keeps an on-device model for good: it is started with that provider and model as its own settings, every later change (the `session_configure` tool, the user's Settings, a changed Agent default) must keep one or is rejected, and a run whose model isn't on-device is refused whatever chose it. It also has no network-egress tools: `web_fetch` and `web_search`, Browser, Computer, image generation and MCP servers are withheld, as are Memory, Knowledge and Skills. Of `agent_manage` it gets only `session_configure`. The target must be a native Agent whose model provider reports `onDevice`; anything else fails the call, and an External Agent can never be a hidden child. The child's transcript is excluded from every Agent tool for all callers (the parent sees only metadata and the final answer), it is never reflected on, its Agent's Memory, Knowledge and Skills tools are withheld, and Notifications about it carry no content. Work a Hidden Session delegates stays hidden. With `review`, the user sees the answer in an Approval in the parent's Session and may withhold it. A parent that runs on-device and delegates to a cloud Agent sends only the goal and context it writes, as for any child.

There is no standalone MCP server for the `kinuvo` CLI yet: the endpoint exists to serve Agents Kinuvo itself runs. Further tools build on the same service ([plan](../plans/2026-11-07-agent-collaboration-design.md)).
