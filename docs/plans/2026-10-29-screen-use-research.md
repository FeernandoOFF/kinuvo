### Interactive streaming, input and authorization

**Source:** Browser view gateway creates bounded sessions, authenticates the member/token or matching tunneled Team session, replaces an old socket, clears old frame geometry on a new stream, serializes incoming input and drops outgoing frames when socket buffering exceeds its threshold. Frame sizes are tracked by sequence for clients acknowledging displayed frames; old/unknown frame references can be refused instead of expanding a click against an unrelated size. [Gateway](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/src/main/browser-view-gateway.ts#L44-L115), [authorization and stream setup](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/src/main/browser-view-gateway.ts#L234-L320).

**Docs + source:** the remote stream uses the existing authenticated tunnel, binary frames and fractional input coordinates; streaming frames are outside the tab operation queue. Capabilities separately advertise browser view, cursor, clipboard, context menu and viewport support. Do not equate view support with every control being available. [Architecture](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/docs/architecture/browser.md#L254-L280).

**Source:** mobile has a real browser screen and tabs route, not merely a desktop mock scaled down. It requests 1280×800, handles its own pointer, keyboard avoidance, safe-area floating controls, navigation/reload/new/close and Takeover completion. Input queue coalesces pointer moves and wheel deltas but flushes before press/release/key; queued input names the previously displayed frame and is flushed before acknowledging the new frame. [Mobile screen](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/apps/mobile/src/features/browser/screens/browser-screen.tsx#L138-L172), [view lifecycle](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/apps/mobile/src/features/browser/components/use-browser-live-view.ts#L45-L125), [input queue](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/apps/mobile/src/features/browser/model/live-view-input-queue.ts).

### Takeover and Approvals are different

**Source:** manual user control stores a local/member/session holder, invalidates refs, blocks new Agent tools, and drains the current tab queue before acquisition completes. Releasing control invalidates refs again and wakes waiters. Closing an owning window/session/member releases its held tabs. A second take returns if already held; release is permitted to any caller that can see the tab, so this is an observed policy, not a design requirement for Kinuvo. [Take/release](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/src/backend/browser-host.ts#L999-L1086).

**Source/docs:** tab-bearing tools have a lowest-level ownership/Takeover gate; agent-wide handling also covers operations such as open/list. Secure-input and card flows add separate protections and user decisions. Secret submission is through dedicated authenticated client messages, not provider tool arguments; unsupported authentication falls back to Takeover. [Ownership/lifetime docs](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/docs/architecture/browser.md#L222-L252), [secure authentication](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/docs/architecture/browser.md#L282-L307).

**Docs limitation:** README and SECURITY explicitly describe `danger-full-access`, `approvalPolicy: never` and first-launch consent. Specific secret/card/MCP user decisions exist, but these do not demonstrate Kinuvo-style per-action Risk/Approval enforcement for ordinary browser actions. Do not import either the blanket access policy or the unrelated CopilotKit action-governance claims. [Security](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/SECURITY.md#L30-L40).

### Agent tools, profiles and lifecycle

**Source:** browser tool catalog includes open/list/status/snapshot, navigate/click/type/fill_fields/press/hover/scroll/select_option/set_checked/drag/upload_files/wait_for/evaluate/set_environment/recording/act/screenshot/close, plus takeover, secret, login/vault and card operations. These are a catalog, not evidence every platform/harness exposes every tool. [Definitions](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/src/backend/browser-tools.ts#L109-L430). Kinuvo should prioritize useful semantic actions and advertised affordances, not reproduce the whole catalog or add arbitrary evaluation merely for parity.

**Docs/source:** Electron persistent partitions support Shared (default), Only this agent, and named shared profiles. Tabs retain their original partition until closed; changing an Agent's assignment closes its tabs but preserves profile data. Named profile deletion closes associated tabs and reassigns Agents; malformed/missing restored profile identities must not silently use another signed-in profile. [Profiles](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/docs/architecture/browser.md#L176-L220), [host partition setup](https://github.com/nightly-labs/openbot/blob/c389f4404256e754214b6982503381778d80ed35/src/backend/browser-host.ts#L2180-L2230).

**Docs:** tabs belong to Agent/thread, outlive turns/cancellation, restore from saved state at restart, unload after idle (30 minutes, five with low memory), and close when Agent is deleted. Restored popups do not retain live opener JavaScript relationships. This differs materially from Kinuvo's removed Browser, whose profiles persist but tabs do not survive Server restart. Persistent cookies, restored tabs, restored page state and replayed input are four different promises.

## Shared interface: useful commonality and real variation

**Proposal:** one controllable-screen contract end to end: discover/select, observe, acquire user control, input, release, reconcile. Give the shared model stable Server+resource identity, availability, optional Agent/Session attribution, control holder/generation, request reason, current activity, capabilities, and frame identity/geometry. Keep Computer and Browser as recognizable source kinds, with typed resource details where needed. Do not turn a Browser into a fake Device/Computer solely to reuse rendering, or expose Playwright/Electron details in product flows.

| Common behavior | Capability-specific variation to retain |
| --- | --- |
| Live view and user control | Device screen may be offline/no screenshot; Browser provisioning may be installing/failed/unsupported. These are orthogonal to control. |
| Semantic capture and input | Computer accessibility ids + capture/app binding; Browser DOM refs + revision/origin/document. Shared freshness semantics, distinct backend validation. |
| Frame/thumbnail | Image dimensions and coordinate space explicit; Computer screenshot pixels differ from desktop window points; Browser viewport CSS pixels may differ from encoded pixel size. |
| Input affordances | Tap/type/scroll/keys common when advertised; browser history/URL/tabs, desktop modifiers/windows/menus and Android Back/Home remain capabilities. |
| Ownership | Computer shared across Agents, paired Device offers tool; Browser Server-owned, profiles per Agent, tabs per Session. Storage ownership is distinct from current controller. |
| Approvals | Tool Risk and Trust/Deny decisions stay in harness; user Takeover is a control decision, not an Approval or automatic Trust rule. |

Behavior, immutable state, selection, validation, lifecycle/reconnect and input ordering belong in `shared/app`; typed wire operations in `shared/protocol`/`shared/client`; common display and responsive controls in `shared/ui`; platform readiness/drivers in expect/actual + Koin. One state data class with orthogonal fields and explicit `val state: StateFlow<S> / field = MutableStateFlow(...)`. Reuse ConnectedServer. Before native iOS integration, read `apps/ios/README.md#swiftui-integration-proof`; native destinations must dispose observers/ViewModels. Embedded Server is another Server; show advertised capabilities, not a ViewModel special case for embedded/mobile.

### Risks that should shape the contract

1. **Takeover boundary race:** Computer sets control before queued perform, but Hand back clears it before its release request obtains the mutex; an Agent may contend at that boundary. Existing queued-action test covers acquiring Takeover, not all release interleavings. Browser serializes commands globally, so acquisition may wait behind a 30-second navigation on another tab. Proposal: atomic acquire/release with acknowledged generation and explicit acquiring state; finish in-flight work before saying user controls it. Never imply an already dispatched action was cancelled.
2. **Multiple management Devices:** both Kinuvo variants hold a global Boolean without authenticated controller identity. Computer disconnect unwatching does not itself clear Takeover; Browser tab persists on Device disconnect. Choose lease/holder/recovery semantics and visibly show who controls it. Losing a view must not silently resume an Agent during sign-in; leaving control permanently stuck also needs recovery.
3. **Approval freshness:** recheck control, ownership, capability, app/origin and capture after an Approval resolves, under the execution gate. Handback invalidates semantic refs; do not automatically replay an approved stale action against new content.
4. **Backpressure:** current Computer watcher produces ~3fps JPEG/base64 into general connection outbox; `offer` disconnects when full. Browser polls all thumbnails and selected capture behind its action mutex and the global Playwright thread. Neither is a dedicated adaptive stream. Proposal: bounded latest-frame delivery separated from durable responses/Approvals, one producer per watched resource, subscriber budgets, visible-only thumbnails, suspend background viewers, prioritize input over captures. A stream need not initially be video to satisfy this contract.
5. **Coordinates:** ComputerInput and Browser user commands do not name the displayed frame. ComputerDisplay decodes asynchronously and retains old bitmap while metadata advances; Browser uses fixed 1280×800 input bounds. Review transform, rotation/resize and frame-image pairing. Bind user input to stream epoch + displayed frame sequence + its coordinate space; reject stale/unknown geometry, account for letterbox/zoom/pan, never silently clamp a tap onto another control.
6. **Reconnect/outcome:** retain last frame only with an explicit stale/reconnecting state; disable input until fresh frame and control reconciliation. Resubscribe/relist idempotently. Do not replay clicks, typing, navigation, form submissions, password entry or unknown-result commands. On timeout, inspect before continuing. Handle late callbacks after selection/Server change; busy Booleans currently do not represent multiple queued operations reliably.
7. **Isolation/security:** profile-per-Agent login persistence is valuable but does not isolate two Sessions using the same account from one another's site-level changes. Private-network browsing is intentional; do not claim SSRF prevention. Management auth, Device tool grants, Agent tool enablement and resource ownership remain separate checks. Revocation must stop views/input immediately. Define handling of sensitive screenshots/thumbnails and error text, not just query-string redaction.
8. **Lifecycle:** preserve no-replay semantics; distinguish profile reset from close tab, Agent setting changes from deletion, viewer disposal from Server shutdown. Provisioning progress/error/cancel should not block all resources or hide a stuck installer. Decide whether persistent tabs are a requirement; do not promise restored interactive page state just because cookies survive.

## Responsive design inputs for Claude Opus

**Proposal:** borrow OpenBot's flow, retain Kinuvo's components and language. Entry from Session activity/Needs you opens the relevant screen directly; broader Computers discovery remains available. Show Agent, Session and Server provenance where ambiguity matters.

- **Desktop:** compact thumbnail overview beside conversation; selecting a card opens large Live view with persistent control status and Take over/Hand back. Browser gets tabs/address/history only when advertised. Computer gets supported Device controls. Keep request reason and Approval context visible without covering the target.
- **Phone:** single full-width Live view, Back to conversation, tab/screen overview in a sheet rather than permanent 126dp rail, safe-area reachable control action, keyboard-aware input tray, pinch/zoom and explicit navigation-versus-remote-scroll gestures. Preserve draft/context when returning. Show a fresh-frame indicator before enabling control.
- **Both:** no tabs/screenshot unsupported, offline/reconnecting, installing/failure/retry, Agent working, Takeover requested, acquiring control, user controls, handback pending, unknown input outcome and access revoked need intentional states. Do not conflate loading, availability, activity and control in one enum. Use Kinuvo's “Approval”, “Live view”, “Takeover”, “Hand back”, “Agent”, “Session”; avoid provider/runtime jargon in normal flows.
- **Accessible input:** announce control changes, label each tab/thumbnail and action, provide keyboard focus and semantic controls independent of screenshot-only pointing, expose only supported keys/actions. UI should explain whether a view is observational or accepts user input.

The requested compatibility workaround is host setting `kernel.apparmor_restrict_unprivileged_userns=0`; document it as an administrator-managed host change, not a silent application action or a universal Linux requirement. Ubuntu and Chromium also document a narrower AppArmor profile with `userns,` for the Chromium executable. [Ubuntu release notes](https://documentation.ubuntu.com/release-notes/24.04/), [Chromium explanation](https://chromium.googlesource.com/chromium/src/+/133.0.6943.53/docs/security/apparmor-userns-restrictions.md).

For an operator choosing the global workaround, document `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` for the current boot, and the same key in an operator-owned `/etc/sysctl.d/60-apparmor-namespace.conf` for persistence. Restore the prior setting/remove that file to undo. This permits user namespaces system-wide and reduces the host restriction; it does not turn Chromium's own sandbox off. Keep `.setChromiumSandbox(true)` and never silently add `--no-sandbox`. Surface actionable launch diagnostics and upstream Linux library prerequisites. ## Suggested design sequence, contingent on sign-off

1. Agree screen/control/frame/capability semantics and responsive state designs, including Approvals and sensitive Takeover.
2. After user sign-off, restore Browser via the explicit removal revert and reconcile current harness composition/API; preserve independent implementation and existing tests.
3. Introduce shared protocol/client/app coordination and backend adapters, preserving Computer app/capture guards and Browser owner/ref guards. Keep compatibility with old management clients and Device drivers through additive capability negotiation; do not change existing wire meanings in place.
