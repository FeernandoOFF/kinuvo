## Recommendation and evidence matrix

**Yes: actual continuous Computer capture is feasible. It is not implemented by the current one-second Computer refresh adapter.** Start with macOS and Android native frame producers, adaptively encoded to independent JPEG images and pushed through Screens. This is continuous capture even when delivery samples or drops frames: the OS supplies buffers in one running session, rather than Kinuvo repeatedly invoking screenshot tools. Do not promise 15/30 fps delivery until measured, and do not impose the superseded arbitrary 4 fps limit.

| Source platform | Kinuvo source evidence today | Continuous native path | Upstream reuse conclusion |
| --- | --- | --- | --- |
| macOS | Desktop app/CLI use `DesktopComputer`, MCP screenshots; no push capture | ScreenCaptureKit `SCStream` callbacks | Existing `cua-driver` exposes recording, not a proven live frame API. Separate `cua-spacesd` has real streaming; different deployment/license. Prefer a small owned capture helper or a narrowly upstreamed driver extension. |
| Android | `AndroidComputer` accessibility screenshots, 350 ms local throttle; Server refreshes about once/second | MediaProjection → VirtualDisplay → ImageReader initially; MediaCodec later | No Android producer found in the inspected cua-driver desktop platform crates. Implement natively in shared UI's Android platform layer. |
| Windows | Desktop wrapper exists, basic actions declared; runtime operation not verified here | Windows.Graphics.Capture; DXGI Desktop Duplication alternative | `cua-spacesd` implements WGC streaming; current Kinuvo adapter does not use it. Feasible follow-up, not current support proof. |
| Linux | Same desktop wrapper/basic action declaration; no compositor/runtime proof | Wayland ScreenCast portal + PipeWire; X11 capture fallback | Upstream spacesd documents X11 and Hyprland paths, not universal Wayland support. Needs desktop-specific validation. |
| iOS | No registered ComputerDriver found; iOS can be a viewer | ReplayKit app capture / user-started Broadcast Upload extension | Conditional viewing/broadcast feasibility, **not** an iOS Computer-control implementation. Do not advertise iOS as a Computer from this research. |

Evidence: local source inspection plus primary upstream/API sources linked below. No build, test, driver execution, capture/recording launch, OS capture prompt, app/Server launch or device operation occurred. The active delegate's unrelated edits were only read. Performance calculations below are hypothetical, not measurements.

## 1. Actual Kinuvo path

Paths are relative to this checkout. App/UI files are an in-flight snapshot and may move as the independent delegate finishes.

1. `apps/desktop/src/Main.kt` registers `CuaComputerDriver`; `apps/cli/src/Computer.kt` supplies `desktop::perform` to a paired `KinuvoClient`. CLI Server entry points expose `--computer`. Desktop source availability is the presence of an executable, not proof that capture permissions work.
2. `harness/plugins/cua/src/DesktopComputer.kt`: `findDriver()` searches PATH, `~/.local/bin/cua-driver`, then `/Applications/CuaDriver.app/Contents/MacOS/cua-driver`. `McpDriver` launches `cua-driver mcp`, speaks MCP over stdio, inspects tool argument schemas, and uses a persistent driver session. It optionally configures `capture_scope=desktop`. `capture()` calls `get_desktop_state(max_image_dimension=1600)`, reads `screenshot_png_b64` or image content, decodes PNG with JVM ImageIO and re-encodes JPEG at quality 0.8. It derives screenshot-pixel/desktop-point scale from the result. Element observations separately call `get_window_state(include_screenshot=false)` and retain handles/capture identity. `perform()` serializes operations under a Mutex; actions can also wait 300 ms before observation. Increasing this call's frequency is still screenshot refresh and shares the semantic execution path.
3. `shared/app/src/device/DeviceAccess.kt` advertises Computer only when a ComputerDriver is available and enabled for that Server. `AppViewModel.kt` wires its callback to `KinuvoClient`. `shared/client/src/KinuvoClient.kt` handles reverse `Api.ComputerAct` (`computer.act`) requests and replies once. `harness/server/runtime/src/ServerRuntime.kt` owns the authenticated paired connection, pending reverse-RPC response map, and `actComputer` callback. `Computers.connect()` associates that callback with the authenticated Device; this supports a remote Computer, not just the Server machine.
4. Android registers `AndroidComputer` in `shared/ui/src@android/Platform.android.kt`. `Computer.android.kt` owns an accessibility service and serialized driver. Accessibility supplies nodes/actions; API 30+ `takeScreenshot(Display.DEFAULT_DISPLAY, ...)` supplies images. The code waits until 350 ms after its previous screenshot, copies the HardwareBuffer to software pixels, scales to a 1024-pixel maximum side, compresses JPEG at quality 70, and base64 encodes. The current `withElements=false` branch returns a screenshot-only `ComputerScreen("frame", ...)` before assigning `last`, preserving the Agent's capture and node handles; only semantic capture updates `last = Capture(id, scale, nodes)`. Preserve that separation in the native producer. The action path still derives gesture scale from `last?.scale`, so native stream geometry needs a separate input binding. The local comment about three screenshots/second is not a guaranteed Android API rate; the public API explicitly exposes an interval-too-short error ([A2]).
5. `harness/server/runtime/src/Computers.kt`: `screen(id)` advertises `ScreenDelivery.CaptureRefresh`, wraps `watch()` in a conflated callbackFlow, and converts ComputerScreen screenshots to ScreenSample. One shared watch job per Computer runs `perform(ComputerRequest(elements=false))` when `FRAME_MS=1000` has elapsed; action results also feed watchers. These calls go through the same serialized request machinery. Current geometry is only width/height/platform: insufficient for general display selection, origin, crop or rotation changes.
6. `harness/core/src/Screens.kt` already provides `ScreenSource.frames(): Flow<ScreenSample>`. `harness/server/runtime/src/Screens.kt` coordinates authenticated management subscriptions and control. `harness/core/src/ScreenView.kt` retains one sent image, one pending/latest image and displayed-frame identity; draw acknowledgements release that view's delivery credit. It validates displayed subscription/epoch/sequence, geometry and control generation before input.
7. `ScreenFrameLane.kt` is replaceable, outside the durable response/Approval outbox: four queued subscription images/connection and a 1 MiB **base64 string length** ceiling/image. `ScreenBudget` permits four subscriptions/authenticated Device across connections. `ServerRuntime` prioritizes queued durable responses before an image write, but cannot preempt an underway socket write (15-second write bound). This is bounded buffering, not a real-time throughput guarantee.
8. `shared/protocol/src/Screens.kt` carries image strings in ScreenSample and subscription/epoch/sequence in ScreenFrame. `shared/client/src/ScreensClient.kt` exposes typed Screens calls/events; `shared/app/src/screen/ScreensRepository.kt` connects them through ConnectedServer. The in-flight `LiveViewModel.kt` owns selection, watch cleanup, displayed-frame acknowledgements and input binding. `shared/ui/src/screen/LiveViewScreen.kt` contains LiveCanvas: base64 decode and `attachmentImage(fullSize=true)` on Dispatchers.Default, atomic bitmap+ScreenFrame pairing, and a draw callback. JVM image rendering uses Skia `Image.makeFromEncoded`, **not ImageIO**; ImageIO is currently in source-side PNG→JPEG conversion. Android/iOS/web image actuals remain platform-specific. This is image rendering, not an H.264 decoder.

Browser is separate: `harness/plugins/browser/src/BrowserRuntime.kt` already uses Chromium CDP screencast, source acknowledgement and a shared producer/tab. Its continuous production does not confer continuous native Computer capture. Retain its independent semantic observations and viewer/source credits.

Support boundaries: `DesktopComputer` labels the current desktop platform and offers basic actions on non-macOS, adding detected advanced tools only on macOS. This is a declaration, not Windows/Linux end-to-end evidence. No ComputerDriver registration was found under iOS/web; the default client callback returns Unsupported. The iOS ComputerScreenshot crop actual in Server runtime is image processing, not an iOS screen capture driver.

## 2. Upstream Cua: what is actually reusable

### Revision and local installation

Inspected public `trycua/cua` main at **`cbe3991f268c7e155bd028fbc9b449b40146cfe9`**, commit timestamp `2026-10-29T15:04:05Z`, obtained via GitHub's commit/tree APIs. Links below pin this revision rather than assuming future main matches. Rust workspace and `@trycua/cua-driver` package both declare **0.38.0** ([U1], [U2]); this is source metadata, not a claim about the latest published release/nightly.

Read-only local evidence: `~/.local/bin/cua-driver` is a symlink to `/Applications/CuaDriver.app/Contents/MacOS/cua-driver`; that app's Info.plist declares **0.8.3**, bundle id `com.trycua.driver`, minimum system 13.0. The executable was not run, and its exact build commit/tool schema was not established. The plist version is not proof of the running daemon's version, permissions, or parity with 0.38.0. Kinuvo currently does not pin a driver artifact version/hash. A guessed `cua-driver-v0.8.3` tag returned 404; do not fabricate a source mapping.

### Driver surfaces

- MCP stdio is the integration Kinuvo uses. The inspected HTTP MCP adapter handles JSON request/response; a transport being called Streamable HTTP is not a video channel. `driver_service_http.rs` routes connection/session operations and invocation, not `/media` live frames ([U3], [U4]).
- The SDK provides same-process Rust runtime, generated UniFFI Python/TypeScript bindings, and versioned C ABI. Inspected SDK exports and ABI header provide operations/completion callbacks, not a demonstrated retained native-frame subscription ([U5], [U6]). Using JNI/FFI alone cannot expose a capability absent from that boundary. A Kotlin binding would also be integration work.
- `start_recording`, `get_recording_state`, `stop_recording` are real tools. macOS `video_sckit.rs` creates SCStream plus **SCRecordingOutput pointing at an MP4 path**, requires macOS 15+, and waits for finalized recording on stop. It is not a live image callback exported to Kinuvo ([U7], [U8]). Recording also stores action/state evidence; it must not become an invisible Live view dependency. Do not tail MP4 files or run recording to simulate an in-memory stream.
- Driver/root source is MIT, including the workspace's license declaration ([U1], [U9]). Optional perception assets have separate licensing (README explicitly distinguishes AGPL icon detector); they are unnecessary for streaming. No need to add them.

The public macOS `capture.rs` exports screenshot functions; core `capture_runtime.rs` re-exports capture-registry types for semantic capture identity, publication and action admission, rather than a retained frame callback ([U18], [U19]). The spacesd backend explicitly describes its own ScreenCaptureKit implementation as temporary/private pending a public driver capture seam ([U13]). A public module named capture is therefore not proof of continuous capture exports.

**Conclusion: no proven drop-in live stream API in the inspected cua-driver interfaces.** Native capture machinery exists internally and could inform an MIT driver extension that adds callback frames, explicit stop/capability/geometry and zero recording. That requires a maintained fork or upstream acceptance, compatibility negotiation, packaging, and TCC identity testing; it is not a configuration switch in the installed driver.

### Separate spacesd: genuine live streaming exists upstream

`libs/cua-spacesd` is a distinct daemon. StreamService exposes `ListTargets`, `OpenMedia`, `SetPreferences`, `RequestKeyframe`, `CloseMedia`; video travels on ticketed **`/media` WebSocket**, optionally QUIC, not on gRPC. The proto defines H.264 Annex B access units with SPS/PPS on keyframes and raw BGRA/debug or PNG alternatives. It supports view-only session policy ([U10], [U11], [U12]). `macos_capture.rs` actually registers SCStream screen output callbacks; `encoded_capture.rs` and `grpc/stream.rs` implement the capture/negotiation path ([U13], [U14], [U15]). This establishes implementation existence, not physical-Mac runtime success here.

It has its own daemon lifecycle, authentication, media tickets and much broader process/filesystem/desktop services. It cannot simply replace `cua-driver mcp`. If chosen later, keep it local/private with narrowly brokered media access; do not grant viewers its root credential or let its input bypass ScreenGate. A remote paired Computer would still need an authenticated bridge into Kinuvo's Server path.

**License distinction:** spacesd's directory LICENSE is **FSL-1.1-MIT**, with competing-use restrictions and an MIT future grant after two years ([U16]); the root MIT license must not be applied to it by assumption. This research makes no determination of Kinuvo's distribution eligibility. Do not copy spacesd capture implementation into Kinuvo as MIT source. Reuse is technically possible as a separately evaluated dependency, but is not the recommended first deliverable given scope, license, deployment and decoder costs.

## 3. Native platform paths

### macOS first

ScreenCaptureKit supplies an actual running SCStream. Enumerate SCShareableContent, select a stable display ID (window filters are also available), configure dimensions/pixel format/interval, attach an SCStreamOutput on a dedicated queue, then consume complete CMSampleBuffers/CVPixelBuffers. Apple documents updating filters/configuration without restarting capture and per-frame content rect/scale metadata ([M1]). Keep the OS queue bounded; Apple's queueDepth guidance defaults to three, never exceeds eight ([M2]). Continuous does not mean generating duplicate frames for a static desktop.

Recommended implementation boundary: a small signed Swift/ObjC helper bundled with the desktop distribution, controlled by a JVM adapter via private inherited pipes and bounded length-prefixed frames. Swift owns SCStream, pixel lifetime, native resize/JPEG encoding, permission/error callbacks and stop. No per-frame JVM PNG decode/re-encode. JNI/C ABI is an alternative but adds callback/thread/lifetime loading complexity; process isolation gives simpler crash cleanup. The adapter contract belongs behind ComputerDriver/ScreenSource; composables receive no platform dependencies. CLI packaging/permission ownership needs an explicit supported identity rather than raw helper launch assumptions.

Screen Recording access is separate from Accessibility input. A new helper may require a distinct grant: the installed driver's grant cannot be assumed to transfer. Apple's sample requires granting access and restarting the app. Upstream embedding docs discuss responsible-process identity but do not prove Kinuvo packaging meets it ([U17]). Use stable signing/bundle identity; report denied/restart-required/unavailable without starting prompts remotely. On stop, last viewer departure, permission loss, display removal, helper crash, source connection loss or app exit: stop capture, release sample buffers/encoder, end the source epoch. Filter/display changes produce new geometry before accepting input. No audio capture or recording by default.

### Android second

Use a locally initiated consent flow: MediaProjectionManager → consent result → a `mediaProjection` foreground service → MediaProjection → one VirtualDisplay whose Surface belongs to ImageReader. ImageReader's latest-image acquisition allows dropping stale buffers; close every Image and release all resources ([A1], [A3]). Copy/resize/encode on a bounded worker, never accessibility main callbacks. MediaCodec input Surface is the later H.264 route ([A5]). Accessibility remains the independent action/semantic provider.

For target Android 14+, declare FOREGROUND_SERVICE and FOREGROUND_SERVICE_MEDIA_PROJECTION, service type mediaProjection; obtain user consent before starting that service and obtain projection inside its lifecycle. Consent is required each projection session; do not reuse a result Intent/token for another createVirtualDisplay. Register onStop; projection cannot be restarted after stop. Use captured-content resize callbacks to resize display/Surface for rotation/window changes instead of creating a second display with the consumed token. Locked screen, system Stop, another projection and process death can terminate capture. Android background foreground-service start restrictions mean a remote watch cannot silently create a new session ([A1], [A6]).

Full display versus single-app capture matters for control: app-only coordinates cannot silently be treated as full-device gesture coordinates. Initially request full-display capture where permitted and validate actual selected geometry; expose view-only/unsupported input if a safe transform is unavailable. `FLAG_SECURE` prevents content in screenshots/nonsecure displays; treat blank/protected output honestly ([A4]). Existing accessibility screenshot remains an explicit fallback when no projection session is active, never relabeled Continuous. Stop projection when the last watch leaves, accepting that the next session needs local consent.

### Windows and Linux follow-up

Windows.Graphics.Capture provides display/window picker, IsSupported, D3D frame pool, FrameArrived and capture session. Offload processing and handle closed targets/resizing; HDR may need tone mapping ([W1]). DXGI Desktop Duplication supplies desktop updates/dirty rectangles; rotation and pointer composition require handling and access-lost requires recreation ([W2]). Both need native integration, session/secure-desktop limitations and packaging proof; OS API existence does not prove Kinuvo desktop input mapping works.

On Wayland, use `org.freedesktop.portal.ScreenCast`: CreateSession → SelectSources → Start (normally user picker) → OpenPipeWireRemote, then consume authorized PipeWire streams. Handle Session::Closed. Query portal/backend capabilities; restoration is permission-dependent, not an unattended universal grant. The current portal v6 docs prefer pipewire-serial targeting over reusable node IDs ([L1]). ScreenCast authorization gives capture, not input authority. X11 can use XShmGetImage with native scheduling/damage-driven updates and shared-memory cleanup ([L2]); this is an explicit X11 fallback, not generic Wayland capture. Avoid spawning per-frame screenshot commands. No Linux/Windows first-stage support claim until those platforms are actually validated.

### iOS boundary

ReplayKit RPScreenRecorder captures an app; a user-started Broadcast Upload extension with RPBroadcastSampleHandler processes screen/audio sample buffers, with start/pause/resume/finish lifecycle; RPSystemBroadcastPickerView provides the user's broadcast selection ([I1], [I2], [I3]). This could become a view-only source, but cannot supply general accessibility traversal/input to arbitrary apps. It is new product scope because Kinuvo does not currently offer iOS as a Computer.

A broadcast extension needs its own Xcode target/bundle/provisioning and Info.plist configuration (RPBroadcastProcessModeSampleBuffer). App Groups entitlement is needed **if** sharing a container/session configuration between host and extension ([I4]); it is not a general screen-control entitlement. Do not invent a mandatory entitlement to unlock unattended system capture. Extension networking, credentials, stop/revoke and memory limits require a separate design. The fetched Apple Markdown metadata gives these legacy ReplayKit symbols availability ranges ending at OS 27; this alone does not establish a replacement API or its capabilities. Recheck the deployment SDK before proposing that implementation. iOS remains a viewer in the recommended scope.

## 4. Capture, encoding, transport and rendering are different work

The pragmatic first lane is native callback buffers → native resize/JPEG → replaceable source upload → Server fan-out → viewer decode/draw acknowledgement. It keeps protocol/UI changes modest and every image independently decodable. It is still bandwidth/CPU intensive; native continuous capture alone does not guarantee smooth Live view.

Illustrative arithmetic, **unmeasured**, using an assumed 100 KiB JPEG:

| Delivered cadence | JPEG payload | Base64 payload, approximately | Bytes encoded/decoded each second |
| --- | --- | --- | --- |
| 15 fps | 1.46 MiB/s | 1.95 MiB/s (16.4 Mbit/s) | 15 independent JPEGs, plus JSON/string allocations |
| 30 fps | 2.93 MiB/s | 3.91 MiB/s (32.8 Mbit/s) | 30 independent JPEGs, plus JSON/string allocations |

These numbers are formula `bytes/frame × fps`, not expected compression or observed bitrate. A 200 KiB frame doubles them. Base64 adds approximately one third; JSON, WebSocket/TLS and acknowledgements add more. Remote Computer → Server ingress happens once; Server egress scales with watchers, not capture producers. Source encode should not repeat per viewer. At 1920×1080 RGBA, one decoded buffer is about 7.9 MiB, or 237 MiB/s of raw pixels at 30 fps before extra copies/GPU upload. This illustrates allocation pressure, not measured process memory bandwidth. Resize early; cap pixel dimensions as well as encoded bytes to prevent decompression bombs.

The existing 1 MiB string limit permits roughly 768 KiB compressed bytes, not a 1 MiB JPEG. Current desktop capture adds PNG decode/RGB copy/JPEG encode; Android adds HardwareBuffer/software copy/resize/JPEG. Native encoding avoids the former round trip, but exact CPU, heat, battery, bandwidth and latency need measurement. Do not infer an achieved cadence from SCStream interval configuration.

The existing client FrameConnection accepts/sends only WebSocket Text frames serialized as protocol JSON; binary media is not enabled merely by WebSocket support.

One outstanding image until draw ack also bounds throughput by end-to-end delivery/ack time: in a simplified otherwise idle link, 100 ms per credit cycle limits delivery to about 10 images/second. This is an arithmetic upper bound, not a latency measurement. Consider a small bounded credit window only after measurement; keep the last acknowledged/displayed identity usable for input and cap in-flight bytes. Cancel/conflate decode before starting obsolete work; native decode may not be cancellable mid-call. Pace publication to rendering, cache at most current/pending bitmaps, avoid ack RPC storms and instrument drops, encode/decode time and queue age.

Binary WebSocket envelopes can remove base64/string overhead on **both** hops while retaining authenticated control messages. They require changes to FrameConnection and each host/client transport implementation, message identity/header limits, stale epoch rejection, fair scheduling and byte budgets; sending binary only Server→viewer leaves source upload overhead. A separate authenticated media connection can reduce response head-of-line blocking but needs scoped short-lived credentials and paired lifecycle. Neither removes network congestion.

H.264/VP8 is a larger media feature. Native encoders (VideoToolbox/MediaCodec) can avoid repeated full images ([V1], [A5]); then specify codec/config, timestamps, access-unit framing, SPS/PPS, IDR requests, geometry/format changes and decoder reset. **Do not put interdependent video frames into an arbitrary latest-only JPEG lane:** dropping reference frames requires dropping until a decodable keyframe or requesting one. New watchers need codec config and a fresh keyframe. Android needs MediaCodec decoding, Apple VideoToolbox/AVFoundation, JVM an actual supported decoder/render bridge, and web a supported WebCodecs/WebRTC path; no universal Compose ImageBitmap video decode exists in this source.

WebRTC adds negotiated codecs, secure media/session signaling, native bindings, ICE/TURN and congestion/recovery machinery ([V2]). It can be a good eventual smooth-remote-view path, but existing Screens is not a WebRTC stack. A direct peer path would change the required Server relay topology and authorization model; use a Server media relay or explicitly scoped relay design. Keep screen audio out of the initial deliverable.

## 5. Proposed paired source subscription contract

This is proposed design, not an existing driver capability or frozen API. Preserve `computer.act` for semantic observation/actions; add optional source-side subscriptions under the **same authenticated paired Device connection**.

- Device advertises capture capabilities separately from input support: delivery modes, target/display IDs, encodings, maximum dimensions, permission/session readiness and actionable unavailable reason. Missing capability selects honest CaptureRefresh. A remote Server is never assumed able to capture its paired Device directly.
- Server→source start/update/stop messages carry source subscription, source epoch, target, requested size/quality/cadence budget and thumbnail/selected demand. Source→Server frame/status messages carry that identity, sequence, encoding, capture timestamp, geometry revision and bounded image bytes. Server validates that the sender owns this paired Computer and still has Computer enabled. An arbitrary Device cannot publish another Computer's frames. Apply negotiated protocol compatibility before advertising the new messages.
- One producer/device/target is reference-counted across Server viewer subscriptions; share one native session per display. Selected demand dominates thumbnail-only demand; avoid starting full-rate capture for overview cards. If several Server connections are supported, the source broker aggregates their authorized leases while keeping each Server's authorization separate. A watch is not permission to activate input, audio or recording.
- Bound raw source buffers, encoder work and source upload to current/latest. Source release/receipt ack means **Server accepted or deliberately discarded that buffer**, not “all viewers drew it.” Ack promptly after bounded acceptance, independently of viewer draw ack. Never block the capture callback on transport; replace obsolete raw frames before paying encode cost. Maintain one producer independently of any slow viewer.
- Server retains one latest source sample and per-view sent/latest state; each viewer has independent credits/byte budget. Add bounded latest-only receiving/decode state client-side rather than trusting a general event SharedFlow to be a media queue. Responses/input/control retain scheduling preference; no claim of preemption on one TCP socket. Limit frames/second and bytes/second adaptively with explicit overload telemetry, not an arbitrary universal fps cap.
- Every complete frame carries immutable target ID, source epoch/sequence, dimensions, source crop/content rect, display origin, scale, orientation and geometry revision. Viewer input references its displayed ScreenFrame plus control generation; Server/source resolve the exact transform associated with that frame. Reject removed displays, obsolete source epochs and mapping changes even when width/height match. A frame binding proves coordinates, not that dynamic content has not changed since capture.
- **Important existing seam to change:** DesktopComputer currently maps user pixel actions through the most recent screenshot's `perPoint`, `screenWidth`, `screenHeight`, and driver session capture state. Merely replacing its screenshot producer can leave input using stale scale/capture tokens. Pass the bound stream transform to a dedicated raw user-input adapter, or explicitly establish a compatible driver coordinate binding without replacing Agent observations. Android likewise needs stream-to-display gesture transforms independent of its last accessibility Capture scale. Do not manufacture a driver capture_id from a frame sequence. Reject input if the driver requires a semantic capture binding that cannot be safely supplied.
- Streaming never enumerates accessibility elements or updates DesktopComputer.last / AndroidComputer.last, Agent capture maps, element tokens or semantic session refs. No per-frame `computer.act` call. Semantic observation can continue on demand while view capture runs. Local phone Takeover state currently arrives in ComputerResult; preserve a separate status/control notification or cheap control-state observation when removing refresh polling, so continuous capture does not hide a local hold/handback. Pixels are not authority over control.
- Start/stop viewing remains independent of ScreenGate Takeover. Watching does not acquire/steal/release control; zero watchers stops capture but does not implicitly hand a held Computer back. Revoke/disable Computer/disconnect cancels associated source leases; last authorized watcher disappearance stops the producer and releases OS resources. Use connection ownership/generation checks so an obsolete disconnect cannot stop a new subscription. Bound orphan leases with expiry/heartbeat in case Stop is lost.
- Source/viewer backgrounding, navigation disposal, Server switch and reconnect all have explicit cleanup. Viewer backgrounding ends its watch; source backgrounding either stops capture or follows a deliberately supported OS service lifecycle (Android projection foreground service), never silently keeps a hidden session. A stopped Android projection cannot be resumed without new local consent. Reconnect creates fresh epochs, discards queued frames/input and renegotiates active capability; no replay of inputs, capture permissions or consumed consent tokens.
- Permission loss, lock, protected content, target removal or encoder failure changes status immediately and disables stale input. No silent polling downgrade presented as Continuous: publish changed delivery/status and let UI show the fallback. Keep images in transient memory, do not append them to Session transcripts, logs, artifacts or recording files. Log only bounded metrics/status metadata.

With later explicit runtime authorization, measure source callback cadence, encoded bytes, dropped frames at each stage, encode/decode CPU and queue age, draw cadence, input-to-visible-result latency, thermal/battery effects and capture shutdown. Use a synthetic moving fixture/counter, no screen recording by default. Compare adaptive JPEG at useful sizes with 15/30 fps target budgets; introduce binary or video only where measured results justify it. Do not borrow upstream benchmark numbers as Kinuvo results.
