# Device reads and journaling

The first Tier 2 slice exposes `device_tools`, `contacts_lookup`, `workouts_list` and `sleep_sessions`. iOS implements all reads; Android implements Contacts. Location history, Health synchronization, Android Health Connect, delegation and voice remain later work.

Settings → This Device's tools enables each source separately for the connected Server. Sources default off. Enabling asks for OS access; reads recheck access, and disabling during a read withholds its result. Existing Agents also enable Device tools in their Agent settings; new Agents include them and `ask_user` in their tool catalog. Existing Agents need `ask_user` enabled to ask journal reflection questions. Results enter the Session transcript and the model context. No bulk data synchronization or local Health cache is created.

Devices advertise the fixed capabilities through `connect` and `device.tools`. The Server sends `device.read` requests, correlated with responses on the authenticated socket. Public Device ids derive from the paired credential's hash through a second hash; display names do not identify Devices. Multiple matching Devices require an explicit `device_id` from `device_tools`.

Background/disconnected Devices cause a waiting form with a Notification through the configured Notifier. Open the Device app to continue automatically, Check again to retry, or Skip to continue without the data. Stop cancels the read and clears the pending form. Waiting runs survive Device reconnects while the Server is running; as with other runs, a Server restart stops them. A Device that has never enabled a source returns unavailable immediately rather than waiting forever.

Health reads accept inclusive local dates, up to 31 days, converted to an exclusive instant range. Workouts and Contacts are capped at 20 records per request and report truncation. Workouts include source, activity code, timestamps, duration, distance and energy when present; routes are excluded. Sleep sessions belong to their local wake date and include the preceding night. They union overlapping samples, exclude awake/in-bed time and select the source with the most recorded sleep per session. Gaps of three hours start another session. HealthKit cannot reveal whether empty results mean no data or denied read access; tools describe that ambiguity and synchronization delays.

Routines can now use `ask_user` and pause for answers before invoking device reads and updating Knowledge. No new scheduled Routine is installed. [Journal conventions](journal-conventions.md) define one daily Markdown Note and an Agent-owned block, refreshed through existing logged, undoable Knowledge tools. [Example journal](example-journal.md) contains labeled sample data for trying the layout.

Agents with both Knowledge and Device tools enabled receive journal instructions at runtime, including the marked-block preservation rules. The user's Knowledge Conventions determine the layout; when no journal layout is defined, the instructions use the daily `Journal` Note described above. The Markdown conventions can also be customized under Settings → Knowledge.

The iOS target declares Contacts/Health read purpose strings and the HealthKit entitlement. Physical-device Health verification needs a provisioning profile that includes HealthKit and a device with Health data. The Android target declares `READ_CONTACTS`; it needs runtime permission. Broad Contacts access for future Play distribution must satisfy the platform's distribution policy; this slice serves the personal app.
